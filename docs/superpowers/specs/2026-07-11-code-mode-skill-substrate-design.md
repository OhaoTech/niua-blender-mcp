# Code-Mode Skill Substrate — Design (increment 1)

**Date:** 2026-07-11
**Status:** approved (brainstorm), pending spec review
**Branch:** lean-rebuild

## 1. Why (the one-paragraph thesis)

A tool-calling agent pays tokens for (1) the tool *definitions* it holds, (2) each call's *arguments*, and (3) each call's *result returned to context*. For a finishing pass — ~8 moves × (checkpoint → act → re-measure readiness → re-measure preservation) ≈ **30–40 tool calls per asset**, each `feedback.*` result a 1–3 KB dict (or a base64 render) — **#3 dominates**: tool-by-tool, all 40 verbose intermediates pile into context and stay there, on top of 300 held tool schemas. **Code mode** emits one script; the 40-call loop runs in the execution environment; **only the final summary returns**. Two wins stack: definitions read on demand as code (~85%, progressive disclosure) and intermediate results kept out of context entirely (the bigger win for a long pass — Anthropic's reference case: 150K → 2K tokens). A finisher is the ideal profile: long, verbose, multi-observe. Crucially, the script calls the *same validated primitives* as functions, not raw `bpy`, so the entire safety contract (typed validation, undo-after-success, main-thread queue) is preserved.

Evidence base (verified 2026-07-11): tool-selection accuracy degrades past ~30–50 visible tools; static catalogs cost tens of thousands of tokens up front; Anthropic's tool-search cuts ~85%; code-execution-with-MCP cuts ~98% by keeping intermediates in the execution environment; skills are an agent-layer SOP that drive tools, graded by an eval. (See conversation sources: Anthropic Agent Skills, code-execution-with-MCP, advanced tool use.)

## 2. Scope

**In (increment 1, substrate-only, in-repo, no LLM, no niua):**
- A tool-client SDK generated from the ToolSpecs (interface layer).
- A Skill abstraction + registry, with the existing finisher ported as skill #1 (finishing layer).
- A code-mode runner + a deterministic token-accounting instrument.
- A LIVE acceptance: readiness parity with the agent baseline + a token-win report.

**Out (increment 2+, explicitly deferred):**
- The LLM authoring/selecting skill scripts (niua orchestrator side).
- Sandbox isolation of skill code (increment-1 skills are our own trusted code).
- Any change to MCP `tools/list` curation (code mode makes it less urgent; separate track).
- Any new skill beyond porting the finisher (the library grows later, each graded).

## 3. Architecture

```
niua ORCHESTRATOR (increment 2 — LLM + sandbox)
      │ picks a skill by name+description (cheap index); emits ONE call
      ▼
SKILLS LAYER  — src/niua_blender_mcp/finishing/skills/  (Part 2, policy, benchmark-graded)
      make_game_ready.run(session, subject, params) -> summary   [finisher ported = skill #1]
      │ calls typed functions
      ▼
TOOL-CLIENT SDK — src/niua_blender_mcp/client/  (interface, generic, zero policy)
      session.mesh.tris_to_quads(object="X")  ->  bridge.call("mesh.tris_to_quads", {...})
      │
      ▼
MCP TOOL SURFACE — Part 1 interface: ~300 validated undo-safe primitives
      │ TCP bridge · main-thread queue · undo-after-success
      ▼
BLENDER
```

**Layer discipline:** the SDK is a pure projection of the tool surface (imports nothing from `finishing`/`evals`) → interface layer. Skills import the SDK (finishing → interface, the allowed direction). `tests/test_layer_boundary.py` must stay green; the SDK package is added to the interface area, the skills package to the finishing/policy area.

## 4. Components

### 4.1 Tool-client SDK (`src/niua_blender_mcp/client/`)

- `client/generate.py` — walks `build_router().specs()` and, for every non-`generated`-tier spec, emits a typed function into a per-domain module. `generated`-tier (RNA passthrough) is excluded from the SDK exactly as it is from `tools/list` (reachable via `capabilities.invoke`). Generated function shape:
  ```python
  def tris_to_quads(_session, *, object=None, face_threshold=40.0, shape_threshold=40.0):
      """Convert selected triangles to quads."""
      return _session.call("mesh.tris_to_quads", _drop_none({
          "object": object, "face_threshold": face_threshold, "shape_threshold": shape_threshold,
      }))
  ```
  - Param names/defaults come straight from `ToolSpec.params` (`Param.default`); required params default to `None` and are dropped if unset so the server applies its own defaults, matching current call semantics.
  - Each generated file carries a header: `# GENERATED by client/generate.py from the ToolSpec surface — do not edit by hand.`
- `client/tools/<domain>.py` — the committed generated modules (mesh, uv, object, feedback, shading, modifiers, io, session, system, scene, geometry, …; one per domain that has ≥1 non-generated spec).
- `client/session.py` — `ToolSession(bridge)`: holds the bridge; `session.call(command, args)` forwards to `bridge.call`; `session.<domain>` returns a namespace whose attributes are that domain module's functions bound to the session (so `session.mesh.tris_to_quads(object="X")` works). Namespacing is done by a small `_DomainNamespace` wrapper, not codegen, to keep generated files flat and diff-stable.
- **Regeneration is deterministic and idempotent**: sorted domains, sorted tools within a domain, sorted params in signature order matching `ToolSpec.params` insertion order.

### 4.2 Skill abstraction + registry (`src/niua_blender_mcp/finishing/skills/`)

- `skills/base.py` — a frozen `Skill` dataclass: `name: str`, `description: str`, `asset_classes: tuple[str, ...]` (informational; which inputs it targets), `run: Callable[[ToolSession, str, dict], dict]`.
- `skills/make_game_ready.py` — the finisher, ported: the identical `MOVES` table and checkpoint→act→re-measure→keep-or-revert loop, but every `bridge.call("x", {...})` becomes `session.<domain>.<tool>(...)`. Returns the same per-move report dict the finisher returns today (`readiness_start`, `readiness_final`, `moves[]`). `TOOLS_USED` is preserved for the runner guard.
- `skills/__init__.py` — `list_skills() -> [{"name","description","asset_classes"}]` (the cheap progressive-disclosure index) and `get_skill(name) -> Skill`.
- **`evals/finisher.py` stays working unchanged** so the existing benchmark `--finisher` path and its tests are untouched. The ported skill and the finisher share behavior; to avoid two divergent copies, `evals/finisher.py:finish` becomes a thin adapter that builds a `ToolSession` around the passed bridge and delegates to the `make_game_ready` skill. (This keeps a single source of the loop logic and guarantees the benchmark still measures the same thing — the byte-identical bench gate proves it.)

### 4.3 Code-mode runner + token accounting

- `scripts/run_skill.py` — CLI: `--skill make_game_ready --items <ids> [--port 8765] [--outdir ...]`. For each item builds the intake (reusing the benchmark's `_build_input`/`_clear_meshes`), wraps the bridge in a **`RecordingSession`** (a `ToolSession` subclass whose `call()` appends `{tool, arguments, result}` to a per-item list before returning — this is where calls are captured, NOT the server's dispatch middleware, since the runner drives the session directly over the bridge, never through the MCP server's `_tools_call`), runs the skill in one pass, then computes the token accounting from the recorded calls. Startup registration guard reuses the benchmark's `assert_tools_registered` with the skill's `TOOLS_USED`.
- `client/accounting.py` — pure, offline-testable. Given a recorded list of `{tool, arguments, result}` calls plus the skill's touched-domain SDK source size:
  - `tool_by_tool_tokens` = Σ over calls of `approx_tokens(arguments) + approx_tokens(full result)` **plus** the advertised schema cost of the distinct tools used (their `input_schema()` JSON).
  - `code_mode_tokens` = `approx_tokens(SDK source of touched domains, read once)` + `approx_tokens(final summary only)`.
  - `approx_tokens(x) = ceil(len(json_or_str(x)) / 4)` — the standard rough estimate; **raw byte counts reported alongside, both labelled approximate**. No tokenizer dependency.
  - Returns `{tool_by_tool_tokens, code_mode_tokens, ratio, tool_by_tool_bytes, code_mode_bytes, n_calls, note}` where `note` states the approximation method.
- Output: `docs/reports/code-mode-token-win.md` — per-asset table (n_calls, tool-by-tool tokens, code-mode tokens, ratio) + the readiness/preservation parity line.

## 5. Data flow (code mode, at runtime)

1. Cheap index: caller reads ~N skill names+descriptions (not 300 tool schemas).
2. Selects `make_game_ready`; (later, an LLM reads the skill code + the touched SDK domains once).
3. One invocation: run the skill on the subject.
4. The skill's full loop runs in the runner against the live bridge — every checkpoint/act/measure/revert — none of it returning to the caller's context.
5. One summary returns; the runner additionally emits the token accounting for the report.

## 6. Testing

- `tests/test_client_sdk.py` (offline): (a) **drift** — `generate.py` output is byte-identical to the committed `client/tools/*.py`; (b) **coverage** — every non-generated spec has a generated function; (c) **dispatch** — calling `session.mesh.tris_to_quads(object="X")` against a fake bridge issues exactly `bridge.call("mesh.tris_to_quads", {"object": "X", ...defaults...})`; (d) `_drop_none` omits unset optionals.
- `tests/test_skills.py` (offline): registry lists the skill with a non-empty description; `make_game_ready.run` against a FakeSession (behavior-driven, same style as the finisher's FakeBridge) keeps/reverts moves correctly; `TOOLS_USED` all registered.
- `tests/test_accounting.py` (offline): on a synthetic recorded run, `tool_by_tool_tokens > code_mode_tokens`, ratio computed correctly, bytes reported, approximation note present; an all-empty run doesn't divide by zero.
- `tests/test_finisher.py` (existing) must stay green — proves the adapter refactor preserved behavior.
- LIVE acceptance (own task): `make_game_ready` on the 5 assets → readiness exactly 0.76/0.80/0.80/0.60/0.64, preservation matches, token table produced; the byte-identical baseline bench (agent mode via the adapter) still holds.

## 7. Constraints carried forward

- Parity green; interface/finishing boundary green (`test_layer_boundary.py`); baseline objective bench byte-identical in baseline mode; **ZERO niua knowledge in code** (the SDK is a generic projection; skills are niua-agnostic finishing policy).
- Every deletion/refactor validated by the full offline suite (currently 773 passed / 71 skipped) + the byte-identical bench.

## 8. Success criteria (definition of done for increment 1)

1. SDK generated, committed, drift-guarded; `session.<domain>.<tool>(...)` dispatches correctly.
2. `make_game_ready` skill ported; `evals/finisher.py` delegates to it; benchmark byte-identical.
3. `scripts/run_skill.py` runs a skill in one pass and emits the token accounting.
4. LIVE: readiness/preservation parity on all 5 assets + a committed `code-mode-token-win.md` showing a materially better ratio (expectation: ≥5×, driven by intermediate-result elision), with the approximation method stated honestly.
